# Beer Search 実装方針

## 1. 目的

Life Atlas 配下に、ビールを提供する飲食店を客観的な情報から検索・比較できる静的検索サイトを構築する。

検索トップは `https://life-atlas.jp/beer/` とし、店舗データ、メーカー認定情報、外部口コミ評価、記事情報を Git 管理された静的データとして保持する。

本機能は「運営者の主観で店舗を順位付けするサイト」ではなく、公開情報・公式認定・外部評価を根拠にした情報基盤を目指す。

## 2. 基本原則

- 客観評価と編集部の感想を分離する。
- 評価スコアは、公式認定情報・公開情報・外部口コミ等、検証可能な根拠から算出する。
- 現地訪問・実食・インタビューの感想は記事として掲載し、原則として客観評価スコアへ直接加点しない。
- 広告・PR・タイアップの有無は評価結果に影響させない。
- 評価・認定そのものについて店舗から料金を徴収しない。
- 出典、確認日、更新日を可能な限り保持する。
- メーカー公式ロゴ・認定マーク等は、利用条件・許諾を確認できない限り使用しない。
- Google 等の外部サービスのデータ取得は、利用規約・API 条件に準拠する。無断スクレイピングを前提にしない。

## 3. URL 設計

```text
/beer/                         ビール検索トップ
/beer/methodology/             評価方法・評価基準
/beer/shops/<slug>/            店舗詳細
/beer/articles/<slug>/         訪問記・インタビュー・特集記事
```

ビール機能は Life Atlas 本体と同一リポジトリ・同一ドメインで運用する。

## 4. システム構成

Astro の静的サイトとして構築する。

```text
src/
├─ pages/
│  └─ beer/
│     ├─ index.astro
│     ├─ methodology.astro
│     ├─ shops/
│     │  └─ [slug].astro
│     └─ articles/
│        └─ [slug].astro
├─ components/
│  └─ beer/
│     ├─ BeerMap.astro
│     ├─ BeerFilters.astro
│     ├─ BeerShopCard.astro
│     └─ BeerScore.astro
├─ data/
│  └─ beer/
│     ├─ shops.json
│     ├─ manufacturers.json
│     ├─ certifications.json
│     └─ rating-history.json
└─ content/
   └─ beer/
      └─ articles/
```

原則としてサーバーサイド DB は使用しない。

GitHub 上の JSON / TypeScript / Markdown を Single Source of Truth とし、Astro ビルド時に静的 HTML / JavaScript へ変換する。

## 5. 店舗データベース

`src/data/beer/shops.json` を店舗マスタとする。

想定項目:

```json
{
  "id": "shop-0001",
  "slug": "example-beer-shop",
  "name": "店舗名",
  "address": "住所",
  "prefecture": "東京都",
  "city": "世田谷区",
  "latitude": 35.0,
  "longitude": 139.0,
  "websiteUrl": "https://example.com/",
  "reservationUrl": null,
  "googleMapsUrl": null,
  "articleSlug": null,
  "certifications": [],
  "externalRatings": {},
  "lastVerifiedAt": "2026-09-09",
  "sources": []
}
```

### 必須管理項目

- 店舗 ID
- slug
- 店舗名
- 住所
- 緯度・経度
- 公式サイト
- 予約 URL
- メーカー認定情報
- 外部口コミ評価
- 記事リンク
- 出典
- 最終確認日

## 6. メーカー認定制度マスタ

4大ビールメーカーの認定・推奨制度について Fit & Gap を実施し、Life Atlas 上で比較可能な共通評価軸へ正規化する。

対象メーカー:

- アサヒビール
- キリンビール
- サッポロビール
- サントリー

メーカーごとの具体的な制度名・認定名称は、実データ投入時に各社公式情報で確認する。

例として以下のような認定・提供品質区分をフィルタ可能にする。

- メーカー公式認定店
- エクストラコールド等の特別提供認定
- スーパーコールド等の特別提供認定
- PERFECT 系の品質認定・推奨情報
- その他、メーカーごとの公式認定・推奨制度

`certifications.json` の想定項目:

```json
{
  "id": "asahi-example-cert",
  "manufacturerId": "asahi",
  "name": "認定制度名",
  "category": "quality",
  "officialSourceUrl": "https://example.com/",
  "lastVerifiedAt": "2026-09-09"
}
```

## 7. Fit & Gap と共通評価軸

各メーカーの認定基準をそのまま点数化するのではなく、認定制度の共通項を抽出して Life Atlas の評価軸へマッピングする。

想定する共通軸:

- サーバー管理
- 洗浄・衛生管理
- グラス管理
- ビール温度管理
- ガス圧・提供設備管理
- 注ぎ方・泡品質
- メーカー公式認定の有無
- メニュー・価格情報の開示
- 営業時間等の情報更新状況
- 予約手段・予約可否

Fit & Gap の結果は将来的に `docs/beer-certification-mapping.md` として独立管理する。

## 8. 外部口コミ評価

Google 等の口コミ評価は「ビール品質そのもの」ではなく、「店舗全体に対する外部評価」として別軸で保持する。

想定項目:

```json
{
  "google": {
    "score": 4.3,
    "reviewCount": 382,
    "collectedAt": "2026-09-09",
    "sourceUrl": "https://..."
  }
}
```

### 更新頻度

初期運用では週次更新を候補とする。

ただし更新頻度は、取得方法・API 制約・運用コスト・店舗数を踏まえて調整する。

- 店舗数が少ない立上げ期: 週次
- 店舗数増加後: 自動更新可能な項目のみ週次、それ以外は月次または差分確認
- 取得失敗時は前回値を残し、`collectedAt` を明示する

## 9. 評価スコア

初期段階では、総合点を無理に一本化せず、複数の客観指標を分けて表示することを優先する。

例:

- メーカー認定状況
- Life Atlas 共通基準への適合状況
- 外部口コミ評価
- 情報開示・予約利便性

総合スコアを導入する場合は、計算式・配点・データソースを `/beer/methodology/` で公開する。

重要原則:

```text
Score = Evidence
Article = Opinion
```

## 10. 記事との接続

現地訪問、実食、店主・スタッフへのインタビューは記事として掲載する。

記事は店舗スコアと分離し、店舗詳細画面に記事が存在する場合のみリンクを表示する。

```text
店舗詳細
  ↓
客観評価
  ↓
メーカー認定情報
  ↓
外部口コミ評価
  ↓
記事がある場合: 「編集部の訪問記事を読む」
```

初期実装ではダミー記事を使用して導線を確認する。

## 11. D3.js 検索 UI

`/beer/` では D3.js を用いて店舗を地図上に表示する。

地図は静的店舗データから生成し、外部地図 API を必須としない構成を優先する。

### フィルタ項目

最低限、以下を選択可能にする。

- メーカー
  - アサヒ
  - キリン
  - サッポロ
  - サントリー
- メーカー公式認定の有無
- 認定制度・提供品質区分
- 都道府県 / 地域
- 外部口コミ評価
- 予約可否
- 記事あり / なし

複数条件を AND / OR で組み合わせられる設計を検討する。

### 店舗選択時

地図上の店舗をタップ / クリックするとカードまたはパネルを表示する。

表示項目:

- 店舗名
- 住所
- 対応メーカー / 認定制度
- 客観評価
- 外部口コミ評価
- 最終確認日
- 店舗詳細へのリンク
- 記事がある場合は記事リンク

モバイルではホバーに依存せず、タップ操作を前提とする。

## 12. 静的アーキテクチャ方針

ブラウザから直接外部サービスへ問い合わせて検索結果を作るのではなく、リポジトリ内の確定済みデータをビルド時に配信する。

```text
公式情報 / 許可された外部データ
        ↓
収集・確認
        ↓
Git 管理された店舗 DB
        ↓
Astro build
        ↓
静的 HTML / JSON / JavaScript
        ↓
D3.js 検索・絞り込み
```

メリット:

- Git で変更履歴を残せる
- 情報更新のレビューが可能
- GitHub Pages と相性が良い
- ランニングコストを抑えられる
- データと画面ロジックを分離できる
- 将来 API / DB 化する場合にも移行しやすい

## 13. データ更新フロー

初期運用:

```text
情報収集
↓
出典確認
↓
shops.json / certifications.json 更新
↓
レビュー
↓
main へマージ
↓
GitHub Actions で静的サイト再生成
```

将来的には GitHub Actions を利用し、許可された API 等から更新候補を取得して Pull Request を自動生成する。

完全自動更新ではなく、公開前に人間が差分確認できる構成を優先する。

## 14. 広告・PR と評価の分離

将来的な収益源:

- PR 記事
- タイアップ記事
- Web 広告
- スポンサー企画
- その他のメディア収益

広告・PR 契約は店舗評価と別管理する。

広告出稿、取材依頼、スポンサー契約等を理由として認定状態・客観スコアを変更しない。

PR / タイアップ記事は利用者が広告であると判別できる表示を行う。

## 15. 開発フェーズ

### Phase 1: データモデル

- メーカーマスタ作成
- 認定制度マスタ作成
- 店舗 DB スキーマ確定
- ダミー店舗データ投入

### Phase 2: 検索 UI

- `/beer/` 作成
- D3.js 地図表示
- メーカー / 認定制度フィルタ
- 店舗カード表示

### Phase 3: 店舗詳細

- `/beer/shops/<slug>/`
- 評価・出典・確認日の表示
- 記事リンク

### Phase 4: 記事

- ダミー記事作成
- `/beer/articles/<slug>/`
- 店舗詳細との双方向リンク

### Phase 5: 更新運用

- 口コミ評価更新方法の確定
- 週次 / 月次更新フロー
- GitHub Actions による更新候補 PR の検討

### Phase 6: 評価基準精緻化

- 4大メーカー認定制度の Fit & Gap
- 共通 Control / メーカー固有 Control の整理
- `/beer/methodology/` 公開

## 16. 今回の非対象

初期版では以下を必須としない。

- 動的データベース
- ユーザーアカウント
- ユーザー投稿口コミ
- 店舗からの認証申請
- 有料認証
- 認証更新料
- 店舗向け管理画面
- リアルタイム予約 API

必要性が確認できた段階で追加する。

## 17. 完了条件

初期 MVP は以下を満たした時点で完成とする。

- `/beer/` が公開される
- 静的店舗 DB から D3.js 地図を生成できる
- 4大メーカーで絞り込める
- 認定制度ごとに絞り込める
- 店舗をタップすると評価情報が表示される
- 店舗詳細へ遷移できる
- 記事がある店舗では記事へ遷移できる
- スマートフォンで検索・選択操作ができる
- 評価と編集部記事が明確に分離されている

## 初期デモ実装（2026-09-09）

- `/beer/` にメーカー・提供品質・エリア・口コミ下限・認定有無・予約可否・記事の有無による AND 絞り込みを実装。メーカー内は単一選択。
- 新潟市の緯度経度から D3 の位置図を生成。道路・海岸線や外部地図タイルを使わず、番号で一覧・選択パネルを関連付け。
- 店舗6件、店舗詳細6ページ、サンプル記事1ページ、評価方法を追加。全店舗・認定区分・点数は架空と表示。
- JSON マスタに出典・確認日・外部評価取得日・記事 slug を用意。実データ未取得は null。
- 認定名・メーカー対応の公式確認、Fit & Gap、口コミ API 利用条件の確定と週次収集は未実施。実店舗投入時にサンプルを置換する。

## 初期エリア・検索仕様の修正（2026-09-09）

- 初期範囲は自由が丘・九品仏・奥沢。region.json で地図中心、範囲、エリア候補を一元管理。既存の新潟ページは変更しない。
- 認定マスタに manufacturerId を追加。未選択時は認定選択を無効化し、選択メーカーの制度だけを候補にする。メーカー切替時は認定条件を必ず解除。
- 実在する制度の名称・公式URL・確認日を登録。店舗への認定付与はすべて架空のサンプルで、実在店の確認とは別。エクストラコールドは提供区分として扱う。
- UIと検索条件の口コミはGoogleのみ。架空の点数を除去し、未取得はnull。最低評価指定時には未取得店舗を除外する。
- externalRatings は評価元をキーにした拡張可能な構成を維持。externalIds.googlePlaceId と importMetadata に将来のリスト取り込み・重複排除用の項目を用意。連携処理自体は未実装。
- GoogleリストURLのみで口コミを自動取得できる前提を置かない。取り込み方式の決定後、許可されたデータを正規化し、出典・取得日・表示条件・保存期限を検証して反映する。
